0：利用制限Gated 0

承認されているのは、旧世代のモデル、または軽量・高速なモデルだけです。AIゲートウェイや独自認証を経由することで遅延が積み重なり、MCPのガバナンスもなく、社内でAIツールへアクセスするには制限があるか、煩雑な手続きが必要です。

Claudeが作成したコードやArtifactsをホスティングするためのIT基盤も承認経路もなく、成果物はローカル環境にしか存在しません。

従来型のセキュリティおよび承認プロセス、成果ではなくトークン単価の抑制に重点を置く判断、意思決定における真に技術を理解する人の声の不足です。
  • Claude.aiのチャット
  • SSO／SCIMとロールベースアクセス制御
  • 組織単位の予算上限
  • 既存の承認プロセスおよびIAMの中に導入
  • データガバナンス一式
ステップ0から1へ進む方法：経営層・購入決定者との認識合わせと、阻害要因のエスカレーション。Claudeを安全に導入するためのフレームワークを整備する。
1：支援あなた＋エージェント（ペア） 約1

一人のエンジニアと一つのエージェントが、主に人間の監督下で動く高速なペアプログラマーです。一度に一つのセッションを実行し、マージ前にほぼすべての変更を確認します。

解放される能力：以前は午後いっぱいかかっていた変更を、会議と会議の間に完了できるようになります。

あなたの注意力と、各応答およびコード編集を確認する必要性です。モデルの出力への信頼が低く、自己検証も不足しているため、すべてを読む必要があると感じ、目を離せません。

作業は同期的です。Claudeが作業している間、次のタスクへ進まず、座って見守ります。
  • Desktop、CLI、IDEでのClaude Code
  • Claude Cowork、Claude Design
  • Anthropic API、Bedrock、Vertex、Microsoft Foundry経由での利用
  • Claude Code分析ダッシュボード＋Analytics API
  • Claude Enterprise向けCompliance API
  • 編集前に意図を確認するPlan mode
  • ユーザー単位の支出上限
  • 中央管理されたモデル／effort設定
  • 中央管理されたポリシー
  • OpenTelemetryエクスポートを既存のSIEM／可観測性基盤へ統合
ステップ1から2へ進む方法：複数のエージェントを同時に実行する。信頼できる自己検証ループ（実際の開発環境を使ったテスト＋ビルド＋Lint＋E2Eテスト）を構築する。権限確認プロンプトで処理が止まらないようAuto modeを使う。コードレビューを自動化する。
2：並列オーケストレーター 約10

一人のエンジニアが、一つずつ独立したworktreeまたはGitチェックアウトを使う5～10個のエージェントを同時に指揮し、それらを行き来します。Claudeは、あなたが確認する前に、テスト、ビルド、Lint、セキュリティスキャンで自身の作業を検証します。Auto modeは常時有効で、自動コードレビューと自動セキュリティレビューも既定で有効です。成果物の量が増え、キー入力の過程ではなく最終的な差分を確認するようになり、保守作業のバックログが減り始めます。コードの大部分をClaudeが書きます。

解放される能力：以前はチームで数週間かかっていたバックログが、一人のエンジニアによる午後のオーケストレーションで進められるようになります。

成果物のレビューです。自分で書くコードは減る一方で、六つの作業ストリームを確認するようになり、レビューがより多くの時間を占めます。

複数のセッションを同時に扱いながら、モデルへプロンプトを与え、方向修正することも負荷になります。
  • Auto mode
  • Agent view
  • Claude Code Review
  • Claude Security Review
  • モバイル版Claude Code、Desktopでのクラウド実行
  • Claude TeamsまたはClaude Enterprise経由での利用
  • Claude Tag（単一タスクを実行）
  • CLIおよびDesktopでのworktree分離
  • Remote controlにより、スマートフォンからエージェントを監視
  • チームの利用状況を監視するAnalytics
  • Lint、自動テスト、型チェックによるコード品質の自動強制
  • ClaudeによるE2E検証（例：Claude Chrome拡張機能またはiOS／AndroidシミュレーターMCPを使用）
  • 人手によるコードレビュー、コードのマージ、セキュリティレビュー。人間が生成したコードとエージェントが生成したコードに同じ品質基準を適用する
  • 一般的で安全なBashコマンドおよびMCPコマンドをsettings.jsonで事前承認する
ステップ2から3へ進む方法：Claudeが文脈を取得できるようにする（コード、Wiki、議論を読めるようにする）。エージェントの裁量とコードレビュー速度を高める（他チームが所有するコードに触れる可能性を含む）。仕事をループと定型処理に分解する。Claudeが別のClaudeを起動できるようにする。
3：監督付き自律マネージャーを管理するマネージャー（組織ツリー） 約100

コードのすべて、またはほぼすべてをClaudeが書きます。「コードを読んだか」ではなく、「モデルにどの文脈が不足していたのか、次回に向けてどう解決するか」が問われるようになります。

解放される能力：以前は人間が手動で開始していた作業を、Claudeが先回りして実行します。担当者が時間を確保するまで待っていた保守やクリーンアップが、バックグラウンドで継続的に動くようになります。

ループへの信頼と、チームの意思決定処理能力です。エージェントのツリーは深すぎて一つずつ見守れません。ループが広く信頼される前にエージェント数を増やすことが落とし穴になります。

利用量の増加に伴い、トークンが効率的に使われていることを保証する必要があります。OTelまたはAnalyticsによる監視と、社内ユースケースがPMF（プロダクト・マーケット・フィット）を得た後はコストを管理しつつ、実験を奨励する文化が必要です。「これは本来、エンジニアが行っていた仕事か」と自問します。
  • worktree分離を備えたサブエージェント（並列エージェント同士の衝突を防止）
  • 反復作業を並列展開するRoutines、/loop、/batch、/goal
  • Dynamic workflows
  • Claude Tag（チャンネルまたはデータソースを監視し、能動的にタスクを開始）
  • 自動コードレビュー
  • 自動セキュリティレビュー
  • エージェントのサンドボックス化
  • 標準をコード化するCLAUDE.mdとSkills
  • チームの利用状況に基づいてAuto modeの分類器を調整
  • モデル選択、advisors、LSP、CLAUDE.mdの遅延読み込みSkillsへの分割により、トークン使用量を管理
ステップ3から4へ進む方法：ドメイン固有ユースケースの自動化を大規模化する（例：コード移行、ファジング、機能開発、フィードバックへの対応）。
4：AIネイティブ意図によって方向づけるVP 約1,000以上

ループは完全に閉じており、ほとんどのエージェントをClaudeが起動します。数百から数千のエージェントが動き、人間は意図によって方向づけ、例外によって監視します。

解放される能力：四半期いっぱいかかっていた移行作業が、開始して進捗を確認するワークフローになります。

仕事を大規模に特定して自動化し、仕事の種類ごとに適切なガードレールを適用することです。
  • エージェントをプログラムから構築・スケジュールするClaude Agent SDK
  • Claude Tag（大部分のSlackチャンネルで稼働し、投稿へ自動応答）
  • 自動化のコスト管理
  • 自動化に使用するモデルの選択
