ハーネス・ハンドブック：進化し続けるエージェント・ハーネスを読みやすく、辿りやすく、編集しやすくする

要旨

現代のAIエージェントの能力は、基盤モデルだけでなく、プロンプトを構築し、状態を管理し、ツールを呼び出し、実行を調整するハーネスにも依存する。モデル、API、実行環境、アプリケーション要件が変化するにつれて、ハーネスには、新しい能力を追加したり既存の挙動を適応させたりするための継続的な変更が必要になる。人間の開発者やコーディング・エージェントがその変更を行う前に、対象となる挙動を実装しているコード上の全箇所を特定しなければならない。

しかし、本番環境のハーネスは大規模で密結合になりやすく、その挙動は複数のファイル、関数、実行ステージ、状態遷移に分散している。一方、変更要求は「システムが何をするべきか」という挙動で記述され、リポジトリはファイル、関数、モジュール単位で編成されている。コード検索、リポジトリ索引、長文コンテキスト処理などの既存手法はコードを調べやすくするが、この二つの表現の対応付けは、依然として開発者やコーディング・エージェント自身が復元しなければならない。したがって、挙動の実装箇所特定（behavior localization）は、ハーネスを進化させるうえで中心的なボトルネックである。

本論文は、ハーネスのコードベースから、静的プログラム解析とLLM支援による挙動構造化を使って自動合成する、挙動中心の表現 Harness Handbook（ハーネス・ハンドブック）を提案する。これは実装知識をシステムの挙動ごとに整理し、各挙動を対応するソースコードへ結び付ける。さらに、高レベルの挙動記述から関連する実装詳細へコーディング・エージェントを段階的に導き、候補箇所を現在のソースに照らして検証する Behavior-Guided Progressive Disclosure（BGPD、挙動誘導型段階的開示）を提案する。

二つのオープンソース・エージェント・ハーネスから収集した多様な変更要求で評価したところ、ハンドブック支援付きの計画は、プランナーが使うトークンを減らしながら、実装箇所特定と編集計画の品質を向上させた。特に、実装箇所が分散している変更、稀にしか実行されないコード経路、モジュール横断の相互作用で改善が大きかった。この結果は、複雑なエージェント・システムを進化させる際には、編集内容を生成することだけでなく、どこを編集すべきかを決めることも重要であると示している。

翻訳上の表記： 本文では behavior localization を「挙動の実装箇所特定」、state register を「状態レジスタ」、function-as-leaf / file-as-leaf を「関数リーフ方式／ファイルリーフ方式」とした。コード識別子、ファイル名、JSONキー、モデル名は原文表記を維持している。

1. はじめに

大規模言語モデル（LLM）の近年の進歩により、エージェント型システムの開発が加速している [1–3]。これらのシステムは、ツール、API、複雑な実行環境と相互作用することで、モデルの能力を拡張する [4–7]。しかし、その相互作用は基盤モデルだけで制御されるわけではない。プロンプトの構築、状態管理、ツール呼び出し、システム構成要素を横断する実行制御を担うハーネスが、それらを調整する。したがってハーネスは、モデルの能力をどのようなシステム挙動として実現するかを決定する。モデル、API、実行環境、アプリケーション要件の進化に応じてハーネスも適応させる必要があり、ハーネスの進化は現代のエージェント開発で繰り返し発生する工学的課題になっている [8–10]。

実務上のハーネス進化では、能力の追加、既存挙動の適応、実行ワークフローの洗練などの変更が必要になる [11, 12]。従来、人間の開発者はリポジトリを読み、関連する挙動を追跡し、その実装を編集してきた。現在は、自然言語による要求から同じ作業をコーディング・エージェントが行うことも増えている [7, 10, 13, 14]。しかし変更要求が説明するのは「どの挙動を変えるか」であり、その挙動が「どこに実装されているか」ではない。変更を人間が行う場合でもコーディング・エージェントが行う場合でも、最初の手順は関連するすべての実装箇所を見つけることである。

本番規模のハーネスで、関連する実装箇所を漏れなく見つけることは難しい [15]。大規模ハーネスは多数のファイルと数百の関数にまたがり、実行ロジックは複数ステージに分散し、共有状態によって接続される。そのため、一つの挙動が、互いに離れた複数の実装箇所に依存することがある。本論文では、挙動として記述された要求に関連するすべての実装箇所を特定する作業を、挙動の実装箇所特定と呼ぶ。大規模で構造的に複雑なハーネス・リポジトリでは、この作業は人間にもコーディング・エージェントにも高コストである。人間の開発者は、システムのメンタルモデルを構築し、ファイルや実行ステージをまたいで挙動を追跡するために多くの時間と労力を要する。コーディング・エージェントにはさらに入力コンテキストの制限があり、関連コードを一度にすべて調べられない。したがって反復的にリポジトリを探索する必要があり、それでも分散した経路や稀にしか実行されない経路を見落とす可能性がある [16, 17]。

既存のリポジトリ理解手法は、コードベースを探索しやすくする。リポジトリ・マップ、コード検索、コード要約、リポジトリ・メモリ、長文コンテキスト編集は、コーディング・エージェントによるコードの発見、調査、保持を支援する [16–20]。しかし、これらの手法はファイル、関数、モジュールを中心に情報を整理する一方、ハーネスの変更要求は望ましい挙動を記述する。個々の関連コード片は見つけられても、それらがどのように協調して挙動を生み出すか、影響を受けるすべての箇所を発見できたかまでは示さない。コーディング・エージェントは、依然として断片を結び付け、要求された挙動と基礎実装の対応を推論しなければならない。本研究が扱うのは、この欠けた接続である。

この隔たりを埋めるため、本論文はシステム挙動とソースコードを接続する運用上の挙動表現、Harness Handbookを提案する。実装知識をファイルや関数ごとに整理するのではなく、「ハーネスが何をするか」によって整理し、各挙動をそれを実装するコードへ直接結び付ける。開発者やコーディング・エージェントは、まず関連する挙動を特定し、そこから対応コードへ直接移動できる。Harness Handbookのインスタンスは、静的プログラム解析とLLM支援による挙動構造化を用いて自動構築する。評価では、二つのオープンソース・エージェント・ハーネスに対する現実的な要求を使い、同一タスクでベースライン計画とハンドブック支援付き計画を比較した。ハンドブック支援は、プランナートークンを減らしながら、実装箇所特定と編集計画の品質を向上させた。この結果は、挙動と実装の関係を明示すると、ハーネス進化の正確性と効率性を高められることを示す。

本論文の貢献は次のとおりである。

  • 挙動の実装箇所特定を、変更要求に記述された挙動を実装するすべてのコード箇所を見つけること、と定義する。完全な編集計画を作る前提として必要な工程である。
  • ハーネスが行うことによって実装知識を整理し、各挙動をソースコードへ直接結び付ける Harness Handbook を提案する。また、静的プログラム解析とLLM支援による挙動構造化を用いて、既存コードベースからハンドブックを構築する自動化フレームワークを開発する。
  • 高レベルの挙動説明から関連する実装詳細へ、コーディング・エージェントを段階的に導くワークフロー Behavior-Guided Progressive Disclosure（BGPD） を提案する。
  • 二つのオープンソース・ハーネスから得た多様な変更要求でHarness Handbookを評価し、ハンドブックを使わない計画と、BGPDに基づくハンドブック支援付き計画を同一タスクで比較する。ハンドブック支援は、プランナートークンを減らしながら、実装箇所特定と編集計画の品質を改善した。

2. 関連研究

本研究は、エージェント・ハーネス、ハーネス進化、コーディング・エージェント向けリポジトリ表現という三つの研究方向と密接に関係する。以下では各方向を簡潔に概観し、挙動の実装箇所特定のための明示的な運用挙動表現を導入する点で、Harness Handbookが既存手法とどう異なるかを述べる。

2.1 エージェント・ハーネス

近年の研究は、基盤モデルを配備可能なエージェント型システムへ拡張する第一級のソフトウェア抽象として、エージェント・ハーネスを捉えるようになっている。Code as Agent Harness は、プロンプト、ツール利用、メモリ、実行ロジックを単なる実装詳細とは見なさず、推論、行動、フィードバック、協調を支える、実行可能で状態を持つソフトウェア層としてハーネスを定式化した [15]。関連するサーベイや工学的研究も、ハーネスを、プロンプト構築、状態管理、ツール呼び出し、制御フロー、外部環境との相互作用を担うランタイム基盤として特徴付けている [21, 22]。

この抽象は、現代のエージェント・フレームワークや本番システムに広く採用されている。AutoGenやOpenHandsなどのフレームワークは、エージェントのオーケストレーション、ツール実行、環境との相互作用、マルチエージェント協調のためのモジュール式ランタイム構成要素を公開している [13, 23]。Claude CodeやCodexなどの産業システムも、信頼性の高い長時間稼働型コーディング・エージェントを構築する主要因として、ハーネス設計を重視している [24, 25]。これらの研究はエージェント・ハーネスの重要性を確立したが、主にハーネスの構築とシステム設計を対象とし、既存の本番規模ハーネスを理解して進化させる問題には焦点を当てていない。

2.2 ハーネス進化

コーディング・エージェントの能力向上に伴い、ソフトウェア工学の取り組みは、機能を人手で実装することから、基礎となるハーネスを自動的に進化させることへ徐々に移行している [7, 13]。近年は、ハーネス工学、適応的ハーネス最適化、自動ハーネス修復に関する研究が始まっている [8, 10, 14, 26–28]。これらの手法は、ハーネス実装を構築、適応、修復することで、エージェント・システムの能力と信頼性を向上させる。

本研究が扱うのは、それらを補完する問題である。ハーネス実装を直接変更するのではなく、ハーネス進化の前提となる課題、すなわち挙動の実装箇所特定を研究する。Harness Handbookは、基礎実装をどのように変更するかを考える前に、開発者とコーディング・エージェントが、挙動変更をどこで行うべきかを特定できるようにする。

2.3 挙動表現

近年、コーディング・エージェントのリポジトリ理解を改善するため、構造的リポジトリ表現、リポジトリ索引、リポジトリ・メモリ、自然言語成果物など、さまざまな表現が提案されている [18, 19, 29, 30]。これらは実装知識を利用しやすい形に整理し、リポジトリのナビゲーション、コード検索、編集を改善する。

しかし既存表現は、根本的には実装中心であり、ソースコード、リポジトリ構造、実行基盤を中心に情報を整理する。分散した実行ステージ、機能モジュール、共有状態をまたいでシステム挙動がどのように生じるかを、明示的には捉えない。これに対しHarness Handbookは、挙動上の要求とその基礎実装を明示的に橋渡しする運用挙動表現を導入し、リポジトリ探索より前に挙動の実装箇所を特定できるようにする。

3. Harness Handbook

Harness Handbookは、エージェント・ハーネスを理解し変更するための三つの要素からなる。第一に、ランタイム挙動を中心としてソースを整理する表現（3.1節）。第二に、リポジトリからこの表現を構築するパイプライン（3.2節）。第三に、ハンドブックを使ってコード変更を導き、空でないリポジトリ差分が生じるたびにハンドブックを自動再同期する変更ワークフロー（3.3節）である。

3.1 Harness Handbookの表現

ソース・リポジトリは、コードがどこに保存されているかを示すが、ランタイム挙動がどのように展開するかを直接は示さない。一つの挙動が、複数のファイル、実行ステージ、共有状態を横断することがある。Harness Handbookは、ソースへのリンクを維持したまま、この情報を挙動中心に再編成する。図1に示すように、L1～L3の文書ツリー D と、それを補完する状態レジスタ・ビュー Z を持つ。

読者は通常、まず L1（システム概要）から読み、アーキテクチャ、実行モデル、主要ステージ、全体のデータフローを把握する。次に、選択したステージの責務、入力、出力、依存関係、ローカル状態を説明する L2（コンポーネント概要）へ進む。最後に L3（ユニット詳細）で、そのステージを、ソースに根拠付けられた実装エントリへ接続する。補完ビュー Z は、ステージ境界を横断する状態関係を記録する。

この表現を有用に保つため、二つの規則を設ける。段階的開示とは、タスクがより詳しい情報を必要とするときだけ、読者がL1からL3へ進むことを意味する。挙動–実装整合性とは、有効なすべてのL3ロケータが現在のリポジトリ上で解決できなければならないことを意味する。ロケータを再検証できない場合、そのエントリを凍結し、更新されるまで実装箇所特定の対象から除外する。したがって、実装詳細については常にリポジトリが権威ある情報源となる。

3.2 Harness Handbookの構築

構築処理は、リポジトリ R からハンドブックを作る。ハンドブックの存続期間中は固定されるリーフ・モード g ∈ {function, file} が、L3エントリの粒度を決める。関数リーフ方式では、各L3エントリが関数全体、または一つ以上の連続領域を表す。ファイルリーフ方式では、各L3エントリが一つのファイルを表す。

二つの方式は、ステージ骨格の取得方法が異なる。関数リーフ方式は、ステージ定義と状態レジスタ定義を含む初期骨格 S0 から始める。ハーネスの実行ステージを忠実に反映する信頼できる初期骨格があり、関数単位のL3エントリが利用可能な予算内に収まる場合に用いる。ファイルリーフ方式は、初期骨格から始めず、ステージ骨格自体を推定する。信頼できる初期骨格がない場合、または関数単位の整理が予算を超える場合に用いる。どちらの方式も3.1節の表現を生成し、付録のアルゴリズム2が両分岐を定義する。

g を選択すると、関数リーフ分岐について図2に示す三つのフェーズで構築する。

フェーズI：静的事実抽出

言語別アダプターがリポジトリを解析し、関数、名前付き外部境界、ソース位置、シグネチャ、呼び出し辺を抽出する。プログラムグラフ G は、内部関数または名前付き境界へ解決できる呼び出しだけを保持する。解決できない呼び出しについて、推測した対象を割り当てることはせず、ログに記録する。このフェーズは決定論的であり、LLMを呼び出さない。

フェーズII：挙動による編成

パイプラインは、選択したリーフ・モードに従って、ソース単位を実行ステージ骨格 S へ整理する。

  • 関数リーフ方式： ソースとコールグラフのコンテキストを使って、関数からステージへの割り当てを提案し、反復的なレビューによって洗練する。一つの関数は、一つ以上の実行ステージに割り当てられる。複数の挙動上の役割を持つ場合は、関数全体ではなく、連続した領域に分けて割り当てることもできる。承認された割り当てと修正によってステージ骨格 S を更新する。
  • ファイルリーフ方式： スキャンしたファイルをカードとして要約し、プログラムグラフと組み合わせてステージ骨格 S を推定する。その後、実行ステージごとにファイルを整理する。任意の提案–レビュー処理によって構造を反復的に洗練できる。未カバーのファイルや未解決の編成上の問題は、Y に明示的に記録したままにする。

付録Aに、両方式の完全な編成手順と検証項目を示す。

フェーズIIで得たステージ骨格とソース編成を、L1～L3の文書ツリーと、ステージ横断の状態レジスタ・ビューへ変換する。各L3エントリを、静的解析で特定したソース位置へリンクし、現在のリポジトリに対して検証する。これにより、ハンドブックからソースまでの追跡可能性を維持する。最後にビュー V をレンダリングし、実装箇所特定と将来の再同期に必要な構造化データをパッケージ化する。

3.3 ハンドブック誘導型の変更と再同期

構築後、ハンドブックはリポジトリ変更のための挙動指向ガイドとして機能する。要求 q が与えられると、ワークフローはハンドブック H と対応するリポジトリ R を使う。リーフ・モード g は処理全体を通じて変更しない。

ワークフローは四段階である。第一に、Behavior-Guided Progressive Disclosure（BGPD）が、粗い情報から細かい情報へハンドブックを辿り、要求された挙動の実装箇所を特定する。関連情報を段階的に開示し、候補ソース位置へ進み、それらを現在のリポジトリに照らして検証する。この処理から、計画の根拠となるソース付き証拠集合が得られる。第二に、プランナーが証拠を編集計画 P とアクション宣言 Γ に変換する。第三に、独立した実行器が P をリポジトリへ適用する。最後に、空でない差分が生じた場合は必ずハンドブックを再同期する。アルゴリズム1に全体ワークフローを示す。

3.3.1 BGPDによる挙動の実装箇所特定

BGPDは、すべてのソース位置を同等に扱うのではなく、ハンドブックを使って粗粒度から細粒度へ候補箇所を絞り、その候補を現在のリポジトリに照らして検証する。

特定処理は実行ステージのレベルから始まる。まず文書ツリー D のL1とL2を使って、要求に直接関係するステージを特定する。次に Z を辿り、共有状態を通じて結合しているステージを追加する。この手順により、構造上は離れていても相互依存するステージを捉えられる。選択したステージ内で、最も関連するL3エントリを選び、そのソース・ロケータを取得する。

続いて、呼び出し関係に沿って候補集合を拡張する。関数リーフ方式では関数コールグラフを、ファイルリーフ方式ではそこから誘導したファイル・コールグラフを使う。外部境界ノードは文脈を提供するが、編集候補として返すことはない。

ここまではハンドブック上で処理する。その後、現在のリポジトリ R を開き、候補ロケータを解決し、要求 q に引き続き関係する箇所だけを残す。これが検証済み証拠 Ebq となる。各レコードは、ファイルパス、任意の関数または領域アンカー、現在のソース抜粋を含む。つまり、ハンドブックが探索を案内し、編集計画の根拠はリポジトリそのものが担う。

3.3.2 編集計画と実行

プランナーは、Ebq を編集計画 P に変換する。各編集ブロックは、変更場所、それを裏付けるソース証拠、変更内容を指定する。対象ファイル、任意の関数または領域アンカー、現在のソース抜粋、意図する変更を記録する。

各編集について、プランナーは対象ファイル、任意のアンカー、三種類のアクション（modify、add、remove）のいずれかを含むアクション宣言も記録する。宣言集合は Γ = (Γmodify, Γadd, Γremove) とする。名前変更は、一つの削除と一つの追加として表現する。

実行器は P を R に適用して更新後リポジトリ R′ を生成し、差分 Δ = Diff(R, R′) を得る。Δ は実際に何が変わったかを示す事実記録なので、ハンドブックの無効化範囲を決める。一方、Γ は、実行が計画どおりであったかの確認にだけ使う。

3.3.3 ハンドブックの再同期

空でない差分 Δ が生じるたびに Resync_g を実行する。可能な限りハンドブック全体を再構築せず、影響を受けた部分だけを更新する。

最初に、変更されたソースを再解析し、プログラムグラフを更新し、旧版と新版を対応付けて追加、削除、変更された単位を特定する。関数リーフ方式では、行番号に依存しないフィンガープリントで関数を対応付ける。ファイルリーフ方式では、ファイル集合の差分と内容ハッシュでファイルを対応付ける。

次に更新範囲を決定する。ステージ骨格 S が引き続き有効であれば、影響を受けたエントリと、それを包含する構造だけを更新する。骨格が無効になった場合は、同じリーフ・モード g と保存済み設定 Θ を使い、更新後リポジトリ R′ に対してアルゴリズム2を再実行する。

最後に、解析または分類できない内容は保守的に扱う。推測して割り当てるのではなく、凍結するかカバレッジ記録に残す。更新が完了すると、新しい組 (R′, H′) が次の要求の開始状態になる。再同期中のモデル呼び出しは、分類、ファイル割り当て、ステージ内編成、説明文の改訂という四つの意味処理に限定され、それ以外はすべて決定論的に実行する。

4. 実験

二つのオープンソース・エージェント・ハーネスを対象に、次の三つの研究質問を評価する。4.1節で実験設定を説明し、4.2節で結果を報告する。

  • RQ1： ハンドブックに誘導された実装箇所特定は、計画コストを削減しながら計画品質を改善するか。
  • RQ2： ハンドブックを使うことで、能力の低いプランナーが、はるかに高能力なモデルと同等の実装箇所特定を実現できるか。
  • RQ3： 改善効果は、要求の種類や実装箇所特定の難易度が変わっても持続するか。

4.1 実験設定

評価方法

本実験は、変更ワークフローにおける実装箇所特定と編集計画を評価する。自然言語の要求が与えられると、NexAU [31] で構築し、DeepSeek-V4-Proで動作する読み取り専用プランナーが編集計画 P を生成する。本実験では、この P の品質を直接採点する。

比較する条件は二つである。ベースラインはリポジトリを直接探索する。ハンドブック支援条件は、BGPDと整合するナビゲーション方針を使い、ハンドブックの案内下で関連ソースコードを特定する。ハンドブックへのアクセスとナビゲーション以外は、要求、モデル、リポジトリ、ツール権限、デコード設定を両条件で同一にする。ハンドブック支援条件で使うハンドブックは、評価対象と同じソースから構築する。

計画品質は、GPT-5.5、Opus 4.8、DeepSeek-V4-Proの三モデルが、それぞれ独立に判定する。

ベンチマークと変更要求

二つのオープンソース・エージェント・ハーネス、Terminus-2 [32] と Codex [25] を評価する。これらは3.2節の二つのリーフ・モードに対応する。Terminus-2には信頼できる初期骨格があるため関数リーフ方式を使い、Codexではリポジトリ規模で階層を推定するためファイルリーフ方式を使う。

各ハーネスから、挙動に基づく変更要求を30件ずつ用意する。要求の種類は次の三つである。

  • Query（Q）： 対象位置を明示せず、既存の挙動を変更する。
  • Cross-file（CF）： 複数のファイルまたはモジュールにまたがる、端から端までの能力を追加する。
  • Search-Hostile（SH）： キーワード検索では見つけにくい位置に、関連実装が存在する。

また、各要求に対して、実装箇所特定の難易度を Easy／Medium／Hard のいずれかに分類する。

評価指標

計画品質、実装箇所特定の正確性、計画コストを評価する。

計画品質： 三つの独立した判定モデルが、各計画を次の三観点で採点する。

  1. Localization（実装箇所特定）： 編集箇所が正確か。
  2. Scope Control（スコープ制御）： 計画が対象に集中し、不必要に範囲を広げていないか。
  3. Reasoning（推論）： 根拠と裏付けとなる証拠が十分か。

重み付きスコアは次式で求める。

S = 0.5 SLoc + 0.25 SScope + 0.25 SReason　（1）

スコアは0～100で、実装箇所特定に最大の重みを与える。ハンドブック支援とベースラインのスコア差が δ = 3 点以上なら高い側を勝者とし、それ未満は引き分けとする。各集計区分の勝率は、その区分における有効な「判定モデル×要求」の比較件数に対する勝利数の割合である。

実装箇所特定の正確性： 予測された各編集計画を、Opus 4.8とGPT-5.5が独立に作成した参照計画と比較する。ファイル粒度およびシンボル粒度で、Recall、Precision、F1、Wrongを報告する。Wrongは、参照計画との重複がゼロだった有効要求の割合であり、低いほどよい。

計画コスト： 実装箇所特定と計画作成で消費したハンドブックおよびソース・コンテキストを含め、要求1件当たりの平均プランナートークン数を報告する。

4.2 実験結果

結果から、三つの一貫した傾向が得られた。第一に、ハンドブックの案内は、プランナートークンを増やさずに計画品質を向上させる。第二に、能力の低いプランナーでも、より強力なモデルが作成した参照計画に近い、ファイル粒度・シンボル粒度の予測を生成できる。第三に、これらの改善は、要求の種類や実装箇所特定の難易度をまたいで持続する。以下、それぞれを詳しく検討する。

ハンドブックの案内によって、能力の低いプランナーが、実装箇所特定で強力なモデルに近づけるかを調べるため、その予測編集箇所を、Opus 4.8とGPT-5.5が独立に作成した参照計画と比較した（表1）。

5. 結論

本研究は、本番規模のエージェント・ハーネスを進化させる際の中心課題として、挙動の実装箇所特定を明らかにし、挙動記述を分散したソース実装へ結び付ける挙動中心表現、Harness Handbookを提案した。Harness Handbookは、リポジトリ知識をランタイム挙動中心に再編成し、ソースから直接この表現を構築し、挙動誘導型段階的開示と自動再同期によって変更を支援する。

実験は、この表現の価値を三つの観点から示した。第一に、ハンドブックの案内は計画コストを下げながら計画品質を改善した。CodexとTerminus-2で、全体勝率はそれぞれ 10.0ポイントと18.9ポイント上昇し、プランナートークン使用量は 12.7%と8.6%減少した。第二に、ハンドブックを使うことで、能力の低いプランナーが、はるかに強力なモデルによる実装箇所特定に匹敵した。二つの独立した参照計画に対する、ファイル粒度・シンボル粒度のRecall、Precision、F1の全24比較が改善した。第三に、改善は要求の種類と実装箇所特定の難易度をまたいで持続した。これらの結果を合わせると、挙動と実装の関係を明示することで、より大きな計画トークン予算を必要とせずに、変更計画と実装箇所特定の効率をともに改善できることが分かる。

Harness Handbookの用途は変更計画に限られない。コードと同期し続ける挙動中心のリポジトリ表現として、挙動監査や回帰影響分析などにも利用できる。次の段階では、ハーネスの自己進化へ適用する。ハンドブックを共有挙動メモリとして使えば、エージェントは、リポジトリの進化に伴う実装箇所特定、計画、実行、再同期のループを自律的に閉じ、ハーネスを自己改善へ近づけられる。

A.1 フェーズI：共通の静的事実抽出

フェーズIは、両方式に共通する一回の決定論的解析である。言語別アダプターが R を解析し、プログラムグラフ G を構築する。内部関数ノードには、関数の完全修飾名、ソースファイル、シグネチャ、行範囲、包含クラス、観測された状態アクセスを記録する。境界ノードは、ライブラリ関数など、名前を持つ外部対象を表す。

グラフが呼び出し辺として保持するのは、対象が内部関数または名前付き境界に解決できる場合だけである。解決不能な呼び出しは、推測した対象を割り当てず、監査ログへ書き込む。このフェーズはLLMを使わないため、後続のすべての編成処理は、同一のソース根拠付き事実から始まる。

A.2 フェーズII：挙動による編成

フェーズIIは、G の事実を実行挙動中心に整理する。出力は、現在のステージ骨格 S と、方式固有の編成状態 Ug である。二つのリーフ・モードは、開始点と整理単位の両方が異なる。

A.2.1 関数リーフ方式

初期割り当て： 関数リーフ分岐（g = function）は、ステージ宣言と状態レジスタ宣言によって S を初期化する、初期骨格 S0 から始める。最初のパスでは、解析可能なすべての内部関数、すなわち合成関数ではなく、有効なソース位置を持つ関数を対象に、一つ以上のステージへの割り当てを試みる。判断には、R 内の関数ソース、G 内の呼び出し元と呼び出し先、現在の近隣割り当て、ステージ記述を使う。通常は関数全体を配置するが、関数の部分ごとに異なる挙動上の役割がある場合は、連続したソース領域へ分割し、各領域を別々に配置できる。

レビューと収束： 一回のパスでは、割り当てまたは初期構造の弱点が明らかになる場合があるため、後続ラウンドで両方をレビューする。各ラウンドでは、まずステージの追加、削除、統合、分割が必要かを確認する。構造変更を承認するのは、変更後の階層が有効であり、すべての状態レジスタ宣言が引き続き存在するステージを参照する場合だけである。承認された変更の影響を受ける関数は、改訂後構造に対して再分類する。

再分類後は、関数全体の配置が周辺ステージと整合しているかを全体監査し、別のパスで保持された領域の境界を修復する。提案変更は、モデルによるレビューを通過してから適用する。ステージ骨格、すべての関数または領域割り当てが前ラウンドと一致し、再検討待ちの関数がなくなった時点でラウンドを停止する。その状態に達しない場合は、Θ に保存された編成予算で処理を打ち切り、残った不足を明示したままにする。

検証と最終化： 承認される割り当ては、有効なステージ名、合法なソース範囲を持ち、競合するアクションを含まないことが必要である。可能な場合、領域境界をパーサーが抽出した文の範囲に合わせ、包含ソースを後の比較用にハッシュ化する。整列できない境界は needs-review とし、フェーズIIIでロケータを有効のままにできるか、凍結すべきかを決める。

決定論的クリーンアップでは、保持領域が同一ステージ内で関数全体をすでにカバーしている場合、その関数が他ステージへ持つ割り当てを壊さず、冗長な関数全体エントリを削除する。その後、ステージ横断参照を再構築し、未マッピングのまま残るすべての関数を記録し、目的とステージ内呼び出しを使って各ステージ内のエントリ順序を決める。提案順序に欠落や重複がある場合は、ファイル順・行順を安定したフォールバックとして使う。最終化された所属、領域アンカーとハッシュ、境界状態、ステージ内順序、未マッピング関数の記録を合わせたものが Ufunction である。

A.2.2 ファイルリーフ方式

ファイルリーフ分岐（g = file）は初期骨格を使わない（S0 = ∅）。まず各ファイルを記述し、その記述から S を推定し、最後に各ステージ内でファイルを整理する。

手順1：各ファイルのカードを作る。 パイプラインは、静的解析で関数を抽出できなかったファイルも含め、スキャンしたすべてのファイルについてカード作成を試みる。正常に生成されたカードは、そのファイルの目的、リポジトリ内の役割、実行ライフサイクル上の位置を説明する。詳細カード生成を有効にした場合は、関数の識別子、シグネチャ、ソース範囲、解決済み呼び出しの静的一覧も含める。モデルはこの一覧を説明できるが、変更はできない。

カード生成には固定されたフォールバック手順を使う。バッチから漏れたファイルは個別に再試行する。詳細カードがなお失敗する場合、ソースを関数範囲のチャンクに分けて再試行する。説明文を一切生成できない場合は、フォールバック・カードを出力し、詳細方式ではグラフ由来の一覧を保持する。そのファイルは後続処理でも利用可能だが、カバレッジ記録 Y では「未記述」として印を付ける。これにより、スキャン済みファイルが黙って欠落することはない。

手順2：ステージを推定し、ファイルを割り当てる。 パイプラインはカードをディレクトリごとにまとめ、その説明を、グラフから得たエントリポイントと解決済み呼び出しに組み合わせる。この文脈から順序付きステージ骨格の案を作り、各スキャン済みファイルを正確に一つの主ステージへ割り当てようとする。説明がある場合はカード記述を使う。その主ステージが、ハンドブック内でのファイルの所属先となる。ロギング、プロトコル、型、設定ユーティリティなど、真に横断的なファイルは、一つまたは二つの副ステージも指定できる。割り当て欠落や未知ステージへの割り当ては、最も近いステージへ強制せず、Y に見える形で残す。

Θ に保存された編成バリアントが、初期結果を洗練するかを決める。既定の oneshot は、ステージ案一回とファイル割り当て一回で終了する。doctor はその案から開始し、レビュー付き洗練ループを適用する。agent はエージェント生成の案から始め、同じループを適用する。エージェントが有効な案を作れない場合はワンショット案へフォールバックする。洗練ラウンドではステージの追加、削除、統合、分割ができ、その後、影響を受けたファイルまたは未割り当てファイルだけを再検討する。すべてのファイルが割り当てられて骨格が安定した場合、カバレッジもステージ均衡も二ラウンド連続で改善しない場合、または編成予算に達した場合にループを停止する。未割り当てのまま残るファイルは、Y に表示し続ける。

手順3：各ステージ内でファイルを整理する。 空でない各ステージについて、まずファイル・コールグラフが「呼び出し元を呼び出し先より先に置く」順序を与える。次にファイルカードを使って、テーマ別グループと読みやすい並びへ洗練する。決定論的チェックで未知パスと重複パスを除去し、割り当て済みの各ファイルが正確に一度だけ現れることを検証する。欠落ファイルはフォールバック・グループに追加し、編成呼び出しが失敗した場合は決定論的な平坦順序へ戻す。この手順はステージ内のファイル順を変更できるが、ステージ骨格そのものは変更できない。

ファイルカード、ステージ割り当て、ステージ内のグループ化と順序、カバレッジ記録 Y を合わせたものが Ufile である。

A.3 フェーズIII：階層合成とパッケージ化

フェーズIIIは、(S, Ug) を文書ツリー D と状態レジスタ・ビュー Z に変換し、再利用可能な生成出力をキャッシュ B に記録し、パッケージ化前に両方をリポジトリに対して検証する。

文書ツリーの合成： 両方式とも、D はL1システム概要、含まれる各ステージのL2コンポーネント概要、ソース根拠付きL3エントリを含む。方式によって合成方向が異なる。

  • 関数リーフ方式はトップダウンに構築する。 既知のステージ骨格をアウトラインとして、L1概要、各L2コンポーネント概要、そのステージのL3エントリの順に生成する。各L3エントリは、そのステージ内の一関数を表す。同一関数に複数の保持領域がある場合は、一つのエントリに統合する。
  • ファイルリーフ方式はボトムアップに構築する。 割り当て済みファイルカードがL3エントリになる。ステージが割り当て済みファイルを所有するか、子ステージを持つ場合に要約し、空の末端プレースホルダーは省略する。残りのステージは葉から上へ処理する。子要約と、そのステージ自身のファイルに対する一行説明からL2コンポーネント概要を作り、最上位要約からL1を作る。

関数リーフ方式では、各L1、L2、L3ノードに、上限付きの「生成–レビュー–改訂」処理を使う。最良の草稿を保持し、評価基準を通過した場合、スコアが改善しなくなった場合、または生成予算に達した場合に停止する。独立したステージは並列処理できるが、一つのステージ内のL3エントリは、後続エントリが先行エントリを参照できるよう順番に生成する。

ファイルリーフ方式では、ファイルカードをそのままレンダリングする。各ステージ要約とシステム要約は一回だけ生成し、失敗時には決定論的フォールバックを使う。親要約は子要約の完了を待つ。得られた説明文と要約は B に保持し、後の生成や再同期で変更のない内容を再利用できるようにする。

状態レジスタ・ビューの構築： 関数リーフ方式では、Z のレジスタ識別子とステージ関係は、現在のステージ骨格にある宣言から得る。生成処理は、その宣言を読者向け説明へ変換するだけで、新しいレジスタを作り出さない。ファイルリーフ方式では、最上位ステージ要約とデータモデル・ファイルの目的から、ステージ横断レジスタを提案する。二ラウンド連続で追加がなくなるか、レジスタ予算に達するまで探索を繰り返す。現在の構造に存在しないステージへの参照は、候補マッピングから除外する。

根拠付けと失敗処理： 合成全体を通じて、R と G の静的事実が権威ある情報源である。モデルは挙動上の説明を追加できるが、ファイルパス、関数識別子、シグネチャ、ソース範囲、解決済み呼び出しを変更できない。配置できない関数やファイルは、推測で割り当てず、明示的に記録する。

レンダリング前に、D 内のすべてのL3ロケータを R に対して解決し、得られたソースを保存済み証拠と比較する。再検証できないエントリは凍結し、更新されるまで実装箇所特定から除外する。これにより、キャッシュから説明文を再利用する場合も、リポジトリを権威ある情報源として維持する。

レンダリングと保存済み同期状態： 検証後、D と Z を読者向けビュー V としてレンダリングする。次に、このビューを、D、Z、固定された g、機械可読な再同期状態 Kg と共に、ハンドブック H としてパッケージ化する。両方式で、Kg は固定リーフ・モード、プログラムグラフ、現在のステージ骨格、方式固有の編成状態、構築設定、生成キャッシュを保持する。保存設定 Θ は、選択した編成または洗練バリアント、カード詳細度、編成・生成・レジスタ抽出の各予算を記録する。関数方式では元の初期骨格 S0 も保持するが、ファイル方式では保持しない。この形で H を保存することにより、後のコード変更時に、変更のない部分を再構築せず、影響を受けた内容だけを更新できる。

付録B　変更と再同期の詳細

本付録では、付録Aで定義したパッケージ契約に基づき、3.3節の四段階変更ワークフローを詳しく説明する。要求 q が、BGPDによる実装箇所特定、編集計画、実行、自動再同期を通る過程を追う。ワークフロー全体で、ハンドブック H は対応するリポジトリ R と組にし、保存済みリーフ・モード g は固定する。

B.1 Behavior-Guided Progressive Disclosure

BGPDは、読み取り専用エージェントを、ハンドブックの粗粒度情報から細粒度情報へ導く。ロケータが証拠集合へ入るのは、現在のリポジトリに対して解決された後だけである。

ステージ選択： ナビゲーションは、H に保存された文書ツリー D のL1とL2から始まる。エージェントはシステム概要とステージ索引を読み、挙動が q と一致する実行ステージを選ぶ。次に状態レジスタ・ビュー Z を辿り、共有状態を通じて結合しているステージを追加する。この手順は、あるステージで書かれ、数ステージ後に消費される値のように、構造上は離れていても相互依存する挙動を回収する。

エントリ選択： 選択したステージ内で、対応するステージページを開き、最も関連するL3エントリを選ぶ。各エントリは要約とソース・ロケータを公開する。本文は必要な場合だけ開示するため、不要なコンテキストを抑えられる。

呼び出し関係による拡張： 候補集合を、同期状態 Kg に保持されたプログラムグラフ G の呼び出し関係に沿って拡張する。関数リーフ方式では関数コールグラフ、ファイルリーフ方式では誘導されたファイル・コールグラフを辿る。名前付き外部境界ノードは文脈を与えることはできるが、編集箇所として返さない。

ソース検証： ここまでの手順はすべて H 上で行う。その後、エージェントは R を開き、各候補ロケータを解決し、q に引き続き関係する箇所だけを保持する。結果が検証済み証拠 Ebq である。各レコードはファイルパス、任意の関数または領域アンカー、現在のソース抜粋を持つ。ハンドブックは探索を案内するが、編集計画の権威ある根拠はリポジトリである。

B.2 編集計画

プランナーは、Ebq を編集計画 P に変換する。各ブロックは、対象ファイル、任意のアンカー、裏付けとなるソース抜粋、意図する変更を指定する。本評価実装では、各変更を原文どおりの old/new ペアとして表現する。各ブロックについてアクション宣言も出力し、Γ = (Γmodify, Γadd, Γremove) にまとめる。名前変更は、一つの削除と一つの追加として符号化する。

B.3 実行

実行は独立したエージェントへ委譲し、このエージェントが P を R に適用して R′ を生成する。変更の事実記録は Δ = Diff(R, R′) である。

本実装の実行器は、ファイルの読み書き、対象を限定した置換、ファイル内検索を行えるが、ディレクトリ一覧の取得やシェルへのアクセスはできない。まず各原文置換を直接適用し、置換に失敗した場合だけ対象ソースを読む。その後、触れたファイルを検証し、設定されていれば対象固有の構文ゲートを実行する。差分 Δ がハンドブックの無効化範囲を決め、Γ は実行が計画に従ったかの確認だけに使う。

B.4 自動再同期

空でない Δ は必ず Resync_g を呼び出し、可能な場合はハンドブックの影響部分だけを更新する。Δ = ∅ なら再同期を省略し、H′ = H とする。

バージョン対応付け： 更新後の R′ を再解析し、更新プログラムグラフ G′ を構築する。Δ を使って、保存済みグラフ G と G′ を比較し、追加、削除、変更された単位を特定する。

関数リーフ方式では、行番号を無視する関数本体フィンガープリントで関数を対応付ける。そのため、単に移動した関数は未変更として扱い、対応する行オフセットだけロケータを移動する。名前変更は、シグネチャ行より下の本体を照合して検出する。ファイルリーフ方式では、ファイル集合差分で追加・削除ファイルを、内容ハッシュで変更ファイルを特定する。そのためパス変更は、一つの削除と一つの追加として現れる。

観測されたアクションと Γ を比較する前に、検出した関数名変更を一つの削除と一つの追加へ正規化する。この監査は、Δ による無効化範囲を変更しない。

範囲限定更新： 次に、現在のステージ骨格 S が変更を収容できるかを確認する。引き続き有効であれば S′ = S とし、Ug の影響部分を U′g へ更新する。

関数リーフ方式では、削除済み所属を除去し、対応付けられた関数を引き継ぎ、新規または変更関数を再分類する。領域アンカー、ソースハッシュ、ステージ内順序、未マッピング状態も更新する。ファイルリーフ方式では、古いカードと割り当てを削除し、新規または変更ファイルのカードを更新し、新規ファイルを割り当て、影響ステージを再編成し、カバレッジ記録 Y を Y′ へ更新する。

次に、影響を受けたL3エントリ、それを包含するL2/L1祖先、依存する状態レジスタを再生成する。これにより、更新文書ツリー D′ と状態レジスタ・ビュー Z′ を得る。影響のない生成出力は B から再利用し、更新キャッシュ B′ はそれらの再利用可能エントリを保持しつつ、更新出力を追加または置換する。

S が変更を収容できない場合は、同じリーフ・モード g と保存設定 Θ を使い、R′ に対してアルゴリズム2を再実行する。関数リーフ分岐は、保存済み初期骨格 S0 も再利用する。ファイルリーフ分岐は、更新後リポジトリから新しいステージ骨格を推定する。完全再構築では、フェーズIが G′、フェーズIIが (S′, U′g)、フェーズIIIの合成が (D′, Z′, B′) を生成する。これらは後述の共通検証・パッケージ化契約に従う。

保守的処理： 解析または分類できないソースを推測で扱わない。ロケータまたはソースハッシュを再検証できない既存L3エントリは凍結し、実装箇所特定から除外する。関数リーフ方式では、マッピングできない新規または変更関数を U′function に未マッピングとして明示的に記録する。変更関数が以前は有効なL3エントリを持っていた場合、分類に成功するまでそのエントリを凍結する。ファイルリーフ方式では、有効なカードまたは割り当てを持たないファイルを、U′file 内のカバレッジ記録 Y′ に残す。

解析、ハッシュ化、グラフ構築、ロケータの繰り越し、カバレッジ確認は決定論的である。モデル呼び出しは、分類、ファイル割り当て、ステージ内編成、説明文改訂に限定する。この分類は完全再構築にも適用する。ステージと関数の判断は「分類」、ファイルからステージへの判断は「ファイル割り当て」、ファイルのグループ化は「ステージ内編成」、カード・文書ノード・レジスタの再生成は「説明文改訂」に数える。

検証とパッケージ化： どちらの更新経路も、付録Aのパッケージ化契約に従う。D′ のロケータを R′ に対して、Z′ のステージ参照を更新骨格に対して検証する。G′、(S′, U′g)、B′、固定 g、Θ（関数方式ではさらに S0）を K′g としてアーカイブし、検証済み (D′, Z′) を K′g と共にレンダリング・パッケージ化して H′ とする。組 (R′, H′) が次の要求の開始状態になる。

C.3 評価条件

ハンドブックの効果だけを分離するため、両条件は同じ設定を共有する。プランナーはNexAU上に構築したエージェントで、基礎LLMはDeepSeek-V4-Pro、リポジトリ・ツールは読み取り専用である。両条件で、要求、リポジトリ・スナップショット、計画契約、デコード設定を同一にする。異なるのは、ハンドブックの利用可否と、それに対応する実装箇所特定の指示だけである。支援用ハンドブックは、評価で使うものと同一のリポジトリ・スナップショットから構築する。

  • ベースライン： ハンドブックを使わず、読み取り専用ツール（ファイル読み取り、ファイル内検索、ディレクトリ一覧）でリポジトリを探索し、編集箇所を特定する。
  • ハンドブック支援： ナビゲーション可能なスキルとしてハンドブックを追加で与え、BGPD方針に従う。ハンドブックからソース・ロケータを提案し、リポジトリに照らして検証する。

ハンドブックはスキルとしてプランナーへ公開する。SKILL.md マニフェストが、いつ、どのようにハンドブックを参照するかをプランナーへ指示し、ナビゲーション対象の参照ファイルを示す。図6にそのマニフェストを示す。両リーフ・モードで同じ構造を使い、各ステージのリーフ・カードは、関数リーフ方式では関数、ファイルリーフ方式ではファイルを保持する。

D.1 ハンドブック生成

以下のプロンプトは、付録Aの構築パイプラインを駆動し、ソース単位を実行ステージへ整理してL1～L3の文書ツリーを合成する。静的に抽出した識別子は全処理を通じて固定し、モデルが生成するのは挙動説明だけである。

D.1.1 関数をステージへ分類する

関数リーフ方式のフェーズIIで、一つの関数を、関数全体または連続領域として、一つ以上のステージへ割り当てるために使う。以下の規則ブロックに続いて、実行時には、利用可能なステージ一覧、関数メタデータ、現在のステージ割り当てを含む呼び出し元／呼び出し先の文脈、行番号付きソースを与える。

あなたは、Terminus 2エージェント・ハーネスの一つのPython関数を解析し、
人手で作成したデータフロー骨格の一つ以上のステージへ分類している。

粒度（GRANULARITY）
- "function"：関数全体を一つの説明単位とする。短く、まとまりのある関数
  （30行以下、または目的が一つで明確な関数）に使う。
- "region"：関数に複数の明確な説明上の段階があり、2～10個の領域へ
  分割すべき場合に使う。複数の判断点や連続フェーズを持つ大きな関数が対象。

領域の規則（granularity == "region" の場合）
- 各領域は連続していなければならず、文の途中ではなく、完全な文の境界で終える。
- first_line と last_line には、領域の最初と最後の行の正確な文字列を入れる。
- 各領域は独自の stage_id を持つ。

ステージ割り当て
- 提供された一覧にあるステージIDだけを選ぶ。
- 多数の場所から呼ばれる小さな横断ユーティリティ（トークン数計算、
  出力長制限、記録マーカーなど）は、crosscut-X* のみに入れる。
  利用側のステージへ重複して追加してはならない。
- self.logger.X を使うだけで、その関数を横断的と判断してはならない。
  主たる役割で割り当てる。
- API表面のメソッド（例：name(), version()）では、
  function_assignments=[]、granularity="function" とする
  （未マッピングの api_surface として記録される）。
- サブシステム内部関数（tmux_session.py / terminus_*_parser.py /
  asciinema_handler.py 内）は、それを駆動する主フローのステージへ割り当てる。

PURPOSEフィールド（60～150語、次の5観点で構成）
1. ACTION：関数が具体的に何をするか（曖昧な "handles" / "manages" は使わない）
2. INPUTS / STATE READ：挙動を決める引数と self._* 属性
3. OUTPUTS / STATE WRITTEN：戻り値と、変更する self._* 属性
4. WHEN INVOKED：誰が、どの条件で呼ぶか
5. NON-OBVIOUS：再試行、フォールバック、読者が見落としやすい設計判断

文脈との整合性
提供された呼び出し元／呼び出し先の文脈を見ること。分類は、それらの現在の
ステージ割り当てと整合していなければならない。たとえば、stage-4.2の領域から
しか呼ばれない関数は、通常stage-4.2付近に属する。

出力
```json フェンス内に、次のJSONオブジェクトだけを返す：
{
  "qualname": "<正確な完全修飾名>",
  "purpose": "<60～150語の5観点説明>",
  "granularity": "function" | "region",
  "function_assignments": ["stage-X", ...],
  "regions": [
    {"line_range":[a,b], "first_line":"...", "last_line":"...",
     "purpose":"<30～80語>", "stage_id":"..."}, ...
  ] | null,
  "file": "<file>",
  "line_range": [<start>, <end>]
}

granularity == "function" の場合、regions = null とする。

D.1.2 関数割り当てをレビューする

提案された各割り当てを、ソース、ステージ定義、呼び出し元／呼び出し先の証拠に照らし、批評役がレビューする。以下のレビュー担当（「エンジニア」）ロール・ブロックに、タスク文脈、レビュー証拠、レビュー対象の提案を続け、最後に出力規則を与える。パイプラインを前進させるため、レビュー担当は APPROVE をやや優先する。

あなたは、AIエージェント・ハーネスのハンドブック内で、関数をどのように
分類・編成するかという提案変更をレビューするシニア・エンジニアである。
懐疑的に検討し、コード挙動に根ざした実質的な懸念を見つけること。

重点項目：
- 提案された分類は、コードレベルで関数が実際に行うことを反映しているか。
- 行範囲／領域境界は、構文上・意味上とも妥当か。
- 横断カテゴリを誤用していないか
  （例：self.loggerを呼ぶだけで "crosscut-X3 logging" と分類する）。
- 呼び出し元／呼び出し先の関係は、提案されたステージ所属と整合するか。

APPROVE、REVISE（具体的な懸念付き）、REJECT のいずれかを選べる。

判断ガイドライン
- APPROVE：細かな表現改善の余地があっても、提案が妥当なら承認する。
  「十分に正しい」提案はREVISEではなくAPPROVEとする。APPROVEには寛大にする。
- REVISE：正確性に重大な影響を与える、具体的で実行可能な欠陥がある場合だけ
  （誤ったステージ、誤った領域境界、コードに関する事実誤認）。文体、言い回し、
  「もっと詳しくできる」といった理由ではREVISEにしない。
- REJECT：提案が根本的に誤っており、改訂では救えない場合だけ。

既定ではAPPROVE寄りに判断する。パイプラインは前進しなければならない。

出力形式
```json フェンス内に、次の単一JSONオブジェクトだけを返す：
{
  "decision": "APPROVE" | "REVISE" | "REJECT",
  "concerns": ["<懸念1>", ...],
  "suggested_revision": { ... } OR null,
  "rationale": "<一文の説明>"
}

- decision == "APPROVE" の場合、concernsとsuggested_revisionは空でもよい。
- decision == "REVISE" の場合、concernsは空であってはならず、各懸念は
  具体的で修正可能な欠陥を指摘しなければならない。
- decision == "REJECT" の場合、concernsは空であってはならず、
  suggested_revisionはnullとする。

D.1.3 ファイルカードを生成する

ファイルリーフ方式のフェーズIIで、スキャンした各ファイルを要約するために使う。ファイルがハンドブックのL3リーフになる詳細方式では、モデルがファイル全体を読み、カード本文を書く。グラフから得た関数一覧、行番号、呼び出し関係は固定事実として供給する。詳細方式のプロンプトは次のとおりである。

あなたはソースファイル全体を読み、ファイルを最小単位（リーフ・ノード）とする
システム・ハンドブック向けに、それぞれのファイルを平易で追いやすい言葉で説明する。
あなたが書く説明そのものが、このファイルに対するハンドブック本文になる。

想定読者：好奇心のある部外者。このプロジェクトには初めて触れ、この分野の
専門プログラマーではない可能性がある。コードベースや専門用語をすでに知らなくても、
このファイルが何をし、なぜ重要なのかを本当に理解できる文章にする。

書き方（内容と同じくらい重要）：
- 日常的で平易な言葉を使う。密度の高い長文より、短く明確な文を選ぶ。
- 仕組みより先に、WHYとWHATを人間の言葉で説明する。このファイルが解く
  現実の問題は何か、なければ何が壊れるか。
- 技術用語や略語が必要な場合、最初に平易な言葉で説明する。
  説明なしの専門用語を残さない。
- 理解に本当に役立つ場合は、短い日常的なたとえを使う。
- 実装上の細部を羅列しない。全体像と直観を優先する。主要な型や関数名を
  挙げてもよいが、何のためにあるのかを必ず平易に説明する。
- 正確さを保つ。単純化しても、事実と異なることは書かない。
- "handles" / "manages related logic" のような空虚な表現を避け、具体的に書く。

各ファイルには、コールグラフから得たFUNCTION LIST
（完全修飾名＋行範囲）も与えられる。関数一覧、行番号、呼び出し関係は事実である。
再列挙してはならない。あなたの仕事は、平易な説明文と、正確な完全修飾名で参照する
各関数の理解しやすい注記を書くことである。

各ファイルについて返す内容：
- "purpose"：新人にも分かる1～2文。このファイルが何のためにあるか。
- "description"：およそ120～300語の読みやすい説明。
  このファイルが解く問題と存在理由、段階ごとの処理、主要部分の連携、
  意外な挙動を平易な言葉で説明する。
- "functions"：ファイルの関数一覧にある各関数について一件。正確な"qualname"で参照し、
  次を含める。
  - "purpose"：関数が何をし、なぜ必要かを平易な1～3文で説明。
  - "data_flow"：何が入る→何をする→何が出る、という前後の物語。
  - "relations"：大きな流れの中での位置。誰がいつ呼び、何へ引き渡すかを、
    提供されたcalls/called-by事実に根拠付ける。
- "role"：次のいずれか正確に一つ：
  entrypoint, orchestration, domain_logic, io_transport, data_model,
  config, util, test, generated, other
- "lifecycle"：実行のどの時点で有効かを示す短いヒント
  （例："startup", "config load", "main loop", "request handling",
   "teardown", "cross-cutting"）。

出力：```json ブロック内のJSONオブジェクトだけを返す：
{
  "purposes": [
    {"file": "<正確なパス>", "purpose": "...", "description": "...",
     "role": "<role>", "lifecycle": "...",
     "functions": [
       {"qualname": "<関数の完全修飾名>", "purpose": "...",
        "data_flow": "...", "relations": "..."}, ...]},
    ...
  ]
}

与えられた各ファイルについて、正確なファイルパスを使い一件ずつ返す。

D.1.4 L1～L3文書ツリーを合成する

二つの方式では、文書ツリーの合成方法が異なる。関数リーフ方式では、各L1、L2、L3ノードを、上限付きのactor–critic–reflexionループで生成する。actorが根拠付き入力からノード草稿を作り、criticが階層固有の評価基準で採点して実行可能な指摘を返し、評価基準を通過するか、スコアが改善しなくなるか、生成予算に達するまでactorが改訂する。L1とL2では長い階層別ライティング・ガイドを使う。L1はホワイトボードで全体を案内するような形式、L2は「問題／主フロー／状態フロー／引き渡し」の構造である。

ファイルリーフ方式では、D.1.3で検証済みのファイルカードがすでにL3本文であり、一回の集約処理でL2コンポーネント概要とL1システム概要を作る。

関数リーフ方式のL3エントリは、正確なソース範囲に根拠付け、次の出力スキーマで生成する。複数領域版では、各領域の説明と、関数全体の設計判断・関係を返す。

D.2 BGPDによる実装箇所特定と計画

以下はハンドブック支援条件で使うBGPDプランナー・プロンプトである。ハンドブックを経由して実装箇所を特定し、候補編集箇所を実ソースに照らして検証してから、自己完結した編集計画を出力する。ハーネスごとに実行時置換するフィールドを {{...}} で示す。

あなたはコードレビュー担当者に代わって、{{PROJECT_INTRO}}への変更を計画する
シニア・ソフトウェア・エンジニアである。

自然言語による変更要求を一つ与える。このフェーズでは、編集内容の正確で
自己完結した計画を作る。ファイル自体は編集しない。別の実行器が計画を機械的に
適用する。各編集について、あなたの正確なOLD文字列を、正確なNEW文字列へ置換し、
ファイルを再読込しない。そのため、計画内の原文文字列はバイト単位で正確でなければならない。

## 二つの成果物、二つの異なる役割
- ハンドブックはハーネスの純粋な位置索引であり、コードの説明そのものではない。
  各関数は一行ロケータとして現れる：
  `<summary><b>Qualified.name</b> -- file:start-end . one-line role</summary>`
  必要に応じてRelationsブロック（呼び出し元／先、レジスタの読み書き箇所）が続く。
  カードには関数本体もソースコードもない。さらに、index.mdはすべてのステージと
  関数ロケータを、registers.mdはすべての状態変数と正確な読み書きコード箇所を列挙する。
  どのファイル、関数、箇所を対象にするかを決めるために使う。これらは、単純なテキスト検索が
  見落としうる、分散した非自明な箇所（別パーサー／テンプレートのミラー、レジスタの全読書き、
  サブシステム横断の接点）を明らかにする。
- 実ソースコードは、何を変えるかについてのGROUND TRUTHである。
  ハンドブックは住所（file:start-end）を教えるが、その住所のコードだけが実際の構造に関する
  信頼できる情報源である。必ず実ソースを読むこと。

## 計画方法――ハンドブックで経路を決め、実ソースを読み、原文どおりの編集を出す
1. 要求の真の意図を理解する。変えるべき挙動差分と、それが修正する状態／条件／値を把握する。
2. ハンドブックで経路を決める。SKILL.md、index.mdの順に読み、その意図が指す
   stages/<id>.md章とregisters.md項目だけを読む。候補集合、すなわち変更が触れるべき
   すべてのファイル＋関数＋アンカーを組み立てる。分散／ミラー箇所に注意する。
   パーサー変更には通常、もう一方のパーサーと両方のプロンプト・テンプレートに双子がある。
   状態変更は、レジスタに列挙されたすべての読み取り箇所へ波及する。
3. 編集予定の各箇所について、実コードファイルをread_fileで読む。正確な本体、制御フロー、
   条件、カードが示唆した役割を本当に持つかを確認する。
4. 各編集について、次の形式の自己完結したEDIT BLOCKを作る。old_stringは、直前に見た
   read_file出力から文字どおりコピーする。記憶から打ち直したり言い換えたりしない。
   空白とインデントを正確に一致させ、変更行の前後に少なくとも3行の文脈を含め、
   ファイル内で一意な断片にする。
5. 変更は、要求に明記されていない結合仮定を壊すことがある。そのような仮定を見つけたら、
   必要に応じて編集または注記を追加する。
6. 要求に必要だと確信できる編集だけを含める。

## EDIT BLOCK形式（実行器が直接適用する）
各編集について正確に次を出力する：

### EDIT <n>
- file: `<作業ディレクトリからの相対パス。例：{{PATH_EXAMPLE}}>`
- where: `<{{WHERE_EXAMPLE}}>` -- この変更が必要な理由
```old
<read_fileから文字どおりコピーした現在のテキスト。空白が正確で一意>
```
```new
<置換後テキスト。正しく慣用的で、意図を実現する最小変更>
```

ブロックの規則（実行器は全面的に信用するため、精度はあなたの責任）：
- oldはファイルの現在内容とバイト単位で一致しなければならない。原文どおりか確信できなければ、
  ブロックを書く前にその領域をread_fileで再読する。
- oldは、一意性を保てる最小範囲にする（通常1～8行）。関数全体を貼らない。
- 同一ファイルの編集は重複してはならない。実行器は上から順に適用し、先行ブロックで変更済みの
  テキストに対して後続ブロックを適用するが、間に再読込しない。したがって同一ファイルの
  あるブロックのold（文脈行を含む）が、別ブロックで変更する行を含んではならない。
  近接して文脈が重なる場合は、一つのブロックへ統合する。同一ファイルのブロックは上から下へ並べる。
- 新規ファイルでは、空の```old```と全内容を入れた```new```を持つ一ブロックを使い、
  whereに"(new file)"と書く。
- 安定した行をアンカーにし、不確かな領域をoldにまたがせない。

完了したらcomplete_taskを呼び、短い編集要約、すべてのEDITブロック、宣言JSONの順で渡す。
このフェーズではファイルを編集してはならない。

付録E　ハンドブック支援付き計画の具体例

本付録では、Terminus-2で実際に行ったハンドブック支援付き実行の一例（ケースQ1、DeepSeek-V4-Proプランナー）を、記録トレースから再構成して説明する。この実行は、BGPDの中心となる二つの動きを具体化する。まずプランナーがハンドブックを経由して、対象とすべきコード箇所を決める。次に、計画を書く前に、各候補を稼働中のソースに照らして検証する。以下のツール呼び出し、ソース・ロケータ、編集はすべて実行記録から得たもので、空白だけを整えている。

変更要求（Q1：完了確認を3回にする）
現在、モデルが task_complete を一度示すと「本当に送信しますか？」の段階へ進み、もう一度示すと採点される。基準を厳しくし、実際に採点する前に、モデルが3回連続で完了を示す必要があるようにしたい。最初の2回は端末状態をもう一度表示し、「本当に送信しますか？」と尋ねるだけにする。

この要求はQuery型である。既存の制御フロー規則を変更するが、ファイル名も関数名も示していない。したがって、プランナーの最初の作業は、完了ハンドシェイクを実装するすべての箇所を見つけること、すなわち実装箇所特定である。

フェーズ1――ハンドブックを経由して対象を絞る

SKILL.md 方針に導かれ、プランナーはソースを一切開く前に、ハンドブックをトップダウンに読み、対象範囲を絞る。

  1. SKILL.md → overview.md（L1）→ index.md：反復ごとの継続と終了を担当するステージを見つける。
  2. stages/stage-4.8.md（Completion Gate）と stages/stage-4.7.md（Command Execute）：ハンドシェイクはCompletion Gateにある。
  3. registers.md：ゲートは状態レジスタ reg-pending-completion によって支えられ、その読み書き箇所はループ、初期化、実行ごとのリセットにまたがる。

ここから二つの事実が得られる。変更対象は一つのステージ（Completion Gate）と一つのレジスタに限定される。一方、そのレジスタの書き込み箇所から、明白なreturn分岐だけでなく、初期化と実行ごとのリセットも一緒に変更する必要があることが分かる。

フェーズ2――稼働中のソースに照らして検証する

ハンドブックは純粋な位置索引でありソースを保存しないため、プランナーは実際の terminus_2.py を開き、各ロケータを確認する。_pending_completion を一度 search_file_content すると7箇所が見つかり、すべて terminus_2.py 内にあった。そのため変更は一ファイル内に収まる。各箇所を読むと、単一のBooleanフラグが、最初の完了マークで設定され、二回目の前に検査され、完了以外のターンと各実行の開始時にクリアされることが分かる。これにより、ハンドシェイクを三つの具体的箇所へ絞り込める。

  • Terminus2.init（約L292）：フラグを初期化する。
  • Terminus2._reset_per_run_state（約L1574）：実行ごとにクリアする。
  • Terminus2._run_agent_loop（約L1427–1440、L1552–1559）：フラグを読み書きする観測分岐と完了ゲート。

編集計画： 箇所を確認した後、Booleanの _pending_completion を整数カウンター _completion_confirmations へ置き換える。ループは完了マークごとにカウンターを増やし、完了以外のターンでリセットし、3回連続したときだけ採点へ戻る。変更集合はすべて terminus_2.py 内の四つの modify アクションである。初期化、実行ごとのリセット、ループ内の二分岐を変更する。完了ゲート自体の代表的編集は次のとおりである。

変更前――2回のBooleanハンドシェイク
if is_task_complete:
    if was_pending_completion:
        # second task_complete: confirmed, grade now
        return
    else:
        # first attempt: ask to confirm, continue
        prompt = observation
        continue
変更後――3回のカウンター
if is_task_complete:
    if was_completion_confirmations >= 2:
        # third consecutive task_complete: confirmed, grade now
        return
    else:
        # first or second attempt: ask to confirm, continue
        prompt = observation
        continue
