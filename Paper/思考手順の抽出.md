## どのように実際の訓練タスクから、どのように、思考のフレームワークを抽出するのか？

中心になるのは、**実行履歴をLLMに読ませて「ほかの問題にも使える手順」を提案させ、その手順を別の検証問題で試す**処理です。この一般化を担当するLLMを、論文では **Refiner（改良担当）**と呼んでいます。

抽出の流れは、次のようになります。

1. **訓練問題を実際に解き、過程と結果を記録する**

   問題文に加えて、「どの順序で行動したか」「ツールから何が返ったか」「最終的に何点だったか」を集めます。ここで材料になるのは、**問題を解こうとした経験**です。

2. **Refinerに、成功・失敗のパターンを考えさせる**

   現在のグラフ、実行履歴と点数、利用可能なツール、過去に却下された修正案を渡します。そして、例えば次のような点を検討させます。

   * 成功した実行では、どの手順が役立っていたか。
   * 失敗した実行では、どの確認が抜けていたか。
   * 同じ操作の繰り返しや、早すぎる終了が起きていないか。

   論文のプロンプトには、**「個々の実行履歴の細部に過適合せず、高い抽象度の概念で記述する」**という指示があります。具体的な経験を再利用可能な型にする部分は、LLMの判断に委ねています。

3. **見つけた改善案を、グラフの変更として出力させる**

   例えば、考察と変更の対応は次のようになります。これは説明用の例です。

   | 実行履歴から立てる改善仮説       | グラフへの反映          |
   | ------------------- | ---------------- |
   | 回答前に制約を確認した方がよい     | 「制約確認」のノードと経路を追加 |
   | 根拠が不足しているのに結論へ進んでいる | 次へ進む条件や注意点を変更    |
   | 同じ検索を繰り返している        | 問題のある経路を削除・修正    |

   出力は、ノード・エッジの追加と削除を指定するJSONです。

4. **検証問題で試して、採用するか決める**

   反復更新の方式では、構造のチェックを通ったグラフを使って、訓練とは別の検証問題を解きます。平均点が現在のグラフ以上なら採用し、悪化したら却下します。これによって、**LLMが考えた一般化が実際に役立つか**を確かめます。

実際の例として、論文の資金管理タスクでは、初回の更新で次の手順が形成されています。

**現金確認 → 資金繰り予測 → メモ保存 → 市場確認 → 資金調達判断**

さらに、後の更新で「月の初めに前回のメモを読み出す」という工程が追加されました。

これを思考の型として言い換えるなら、**「現状を確認し、先を予測してから判断する。その判断に必要な情報を、次回にも引き継ぐ」**となります。この言い換えは私の整理ですが、元になった手順の生成・追加は論文に記載されています。

つまり、抽象化の能力は既存のLLMから借りています。**経験から改善仮説を作る役割をLLMが担い、その仮説を残すかどうかを実行評価で決める**という設計です。得られる型は、その訓練タスク群や利用可能なツールに合わせたものになります。
