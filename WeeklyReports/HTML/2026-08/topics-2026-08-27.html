原文
Question I keep getting: why GGUF for Flash-Next instead of NVFP4, since Blackwell loves NVFP4 and it crushed it for DS V4 Flash and Qwen3.8-27B for me. Answer: fit, not preference. The official NVFP4 checkpoint is 135GB. Not because the experts are big, but because the 51B n-gram table ships as FP8 inside it, untouched. That's over my 128GB before a single KV token. GGUF won because llama.cpp lets me pin that one tensor to the CPU backend and mmap it from SSD, while everything else runs resident on GPU. NVFP4 serving engines don't expose that split today. So this isn't NVFP4 losing on merit. It's a checkpoint that bundles a lookup table with the compute weights, on hardware where you'd want to treat them completely differently. The moment someone ships an NVFP4 build with the table separated, I'm switching. Unfortunately, I don't have the hardware for building my own models.日本語訳よく訊かれる質問: Blackwell は NVFP4 が得意で、DS V4 Flash や Qwen3.8-27B では自分も NVFP4 で圧勝したのに、なぜ Flash-Next は GGUF なのか。 答え: 好みではなく「収まるか」だ。 公式 NVFP4 チェックポイントは 135GB。エキスパートが大きいからではなく、51B の n-gram テーブルが FP8 のまま手を付けられず同梱されているから。KV を 1 トークンも積む前に 128GB を超える。 GGUF が勝ったのは、llama.cpp ならその 1 テンソルだけを CPU バックエンドに固定して SSD から mmap し、残りは全て GPU 常駐で回せるから。NVFP4 のサービングエンジンは今日その分割を露出していない。 つまり NVFP4 が実力で負けたのではない。ルックアップテーブルを計算重みと束ねたチェックポイントを、本来は全く別扱いしたいハードで動かしているだけ。テーブルを分離した NVFP4 ビルドが出た瞬間に乗り換える。あいにく自分でモデルを作るハードは持っていないが。
