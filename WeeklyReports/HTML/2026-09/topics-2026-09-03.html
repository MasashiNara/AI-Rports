AIでコード生成量が増え続ける中、人間がすべてを丁寧にレビューするのは持続可能なのか？ AI時代に「人間による厳密なレビュー」をどう残すか、という話が面白い。ポイントは、単純にレビューをAIに置き換えるだけではなく、人間が深く理解すべき変更と、AIに任せられる変更を分けること。 レビュー負荷が・・・とか言っていてもまわらないものはまわらないし、レビューばかりしていたらレビューの品質も下がっていく。レビュワーのモチベーションも下がっていく。自分たちで自分たちの開発プロセスをメンテナンスしていく時代ですね。 以下、詳細です。 ・AI生成コードの最大の問題は、品質以前に圧倒的なレビュー量 ・しかもAIのコードは一見もっともらしく見えるため、微妙な問題を見つけるにはむしろ高い集中力が必要 ・全部を厳密にレビューする → AI時代には量的に厳しい ・ざっと見るだけ → チームの理解が失われ、「認知負債（Cognitive Debt）」が蓄積する そこで提案されているのが、変更の性質によってレビュー方法を変えること。 低リスクな変更 → AIレビューを活用し、人間同士のレビューを省略する 複雑・重要な変更 → まず人間自身が実装案を作り、問題と解決策を深く理解する。その後AIに改善案を出させ、人間が一つずつ判断する つまり、AIに先に考えさせて人間が確認するのではなく、人間が先に理解してAIを使う。 さらに面白いのがコードオーナーシップ。自分が深く理解し責任を持てる領域なら、他の人のレビュー待ちをせず、AIレビューだけでマージできるようにする。ただし、少数のコードオーナーしかいなければ、その人たちにレビューが集中してしまう。 だから、多くのエンジニアがコードオーナーであること ＋ 小さなチームであること が重要になる。 一言でいうと、AI時代に必要なのは、人間のレビューをなくすことではなく「人間がレビューすべき場所」を絞ること。そして、その前提になるのが、「このコードを誰が深く理解し、責任を持っているのか？」 AIによってコード生成が高速化するほど、コードオーナーシップと人間の理解が重要になる。

Anthropic Released Claude Commerce Agents: An Apache-2.0 Blueprint for Shopping and Merchant Agents Across Retail, Travel, Telecom, and Entertainment. No intent router. No subagent per domain. No custom markup for the UI. Here's how it works. 👇 1. One agent loop, skills for the long tail A commerce session is one tightly coupled conversation across many intents. Every handoff to a subagent is state-lossy — the orchestrator holds the cart, the preferences, the history. → Anthropic reports a single agent with skills beat both the one-big-prompt and the subagent design on quality, often at lower cost and latency 2. Prompt or skill, decided by frequency Loading a skill costs a model turn, so anything the agent needs on most turns goes in the system prompt. Safety rules, brand constraints, and key user facts always sit there. → Roughly a third or more of traffic → system prompt; everything else → skill → 5 skills on the shopping agent, 5 on the merchant agent 3. UI components are tools, not tags Most commerce responses are carousels, itineraries, and seat maps. The model calls present_products or present_itinerary with typed arguments; the server validates and the client renders. → The layout lives in the messages array, so "the third one down" resolves 4. Prompt caching carries the cost Caching is prefix-based, so the request is ordered global → session → volatile. A timestamp at the top of the system prompt breaks the cache on every request. → 90–99% hit rate is the range Anthropic says to design for → Cached reads cost a tenth of fresh tokens; cache writes carry a ~1.25x premium @AnthropicAI日本語訳Anthropic が Claude Commerce Agents（小売・旅行・通信・エンタメ横断の Apache-2.0 ブループリント）を公開。インテントルータなし、ドメインごとのサブエージェントなし、UI 用の独自マークアップなし。仕組みは以下。 1. 1 つのエージェントループ、ロングテールは Skills で：コマースのセッションは多数の意図が密結合した一続きの会話。サブエージェントへの受け渡しは毎回状態を失う（カート・嗜好・履歴はオーケストレータが保持）。→ Anthropic は、Skills を持つ単一エージェントが「巨大プロンプト」型にもサブエージェント型にも品質で勝り、しばしば低コスト・低レイテンシだったと報告。 2. プロンプトか Skill かは頻度で決める：Skill のロードは 1 ターン分のコスト。ほぼ毎ターン要るものはシステムプロンプトへ（安全規則・ブランド制約・重要なユーザー情報）。→ トラフィックの約 1/3 以上→システムプロンプト、それ以外→Skill。ショッピング側 5・マーチャント側 5 Skill。 3.
